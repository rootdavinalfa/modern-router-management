## Concerns
1. **Security mode is read-only, not a free-form Select** (deviation from the brief's sketch, deliberate): `WifiConfigDTO` has no security field and the driver cannot change security mode; an editable control would silently no-op. Documented in-UI ("Reported by the router — the security mode is read-only here."). If router-side security switching becomes a future driver capability, promote this to an editable Select.
2. **Live save NOT exercised** (read path only). The router credentials' decrypted password is unavailable to this task, and the driver's update ALWAYS rewrites the passphrase (write-only — it cannot diff against the encrypted stored value) plus re-read-confirms. A same-value apply would require the real passphrase; not attempted to avoid a destructive password change on the user's production router (T7 caution mirrored). Mutation wiring proven via intercepted POST body == exact `WifiConfigDTO`; error path + validation proven. A live same-value apply with the real password remains the recommended final check (as in T7).
3. **Channel select narrowed to the F6600P's actual options** (2.4G 1–11, 5G 36/40/44/48/149/153/157/161/165) rather than the full schema 1–165 — mirrors what the driver's own adconf `UI_Channel` select offers (T7 live capture). Schema-legal but router-illegal channels (12/13/14 on 2.4G) are intentionally excluded; a channel not in the list can't be sent, which is safe.
4. **Vite dev churn during browser tests** (deps re-optimization + ssr page reloads mid-verification caused transient blank-page states) — an environment artifact of the first-run dev server, not the app; re-verified stable across 60s+ afterwards.
5. WiFi changes affect device signal readouts, but invalidation is intentionally scoped to `['router', id, 'wifi-status']` per the brief ("keep scope"); devices self-refresh on their 15s interval.

## Review fix round 1 (commit c4c53af)

Review of c67fc59 returned 2 Important + 3 Minor findings; all fixed in `c4c53af`.

### Fixes (apps/web/src/features/wifi/wifi-band-form.tsx + wifi-page.tsx)

- **Important (a) — reset wiped typed password on background refetch.** The reset `useEffect` depended on the `current` prop object, whose identity changes every parent render (`currentFor` builds a fresh literal), so refetchOnWindowFocus/background refetches fired `reset({password:''})` mid-edit. Fix: derive primitive deps (`reportedEnabled`/`reportedSsid`/`reportedChannel`, each defaulted) and reset only when those actual values change. Password is never re-seeded, so a status refetch reporting identical values no longer clears the user's typing.
- **Important (b) — 'No Security' band silently no-oped.** With security `'No Security'` (driver `securityFromAp` maps None/WEP → `'No Security'`) the form previously rendered a hidden `password=''`; zod blocked submit but the error only rendered inside the password branch, so "Apply settings" did nothing with no message. Fix: (1) the hidden input is replaced by a visible muted note — "This network has no password — SSID and channel changes cannot be applied until the security mode supports one."; (2) the submit button is now `disabled={!passwordRelevant || isAnySaving}` — never a silent no-op.
- **Minor (a)** — removed the dead `export type WifiConfigDTO = z.output<...>` re-export from wifi-band-form.tsx (page imports the canonical type from `@modern-router-management/types/router`).
- **Minor (b)** — missing-band default channel is now `CHANNELS_BY_BAND[band][0]` (2.4G → 1, 5G → 36) instead of a hard-coded 1 that is illegal on 5 GHz; the default always matches a rendered option.
- **Minor (c)** — both bands' Apply buttons disable while any save is pending (`isAnySaving={updateMutation.isPending}` passed to every form). A second band's submit can no longer supersede an in-flight save on the shared mutation keyed by `variables.band`.
